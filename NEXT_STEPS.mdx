**sidecar** (`localmodel-lm`, Swift) that serves local models (MLX today, Core AI scaffolded).

### Protocol (sidecar)
- stdin: `{"session_id","prompt","role?"}` (one JSON per line)
- stdout: `{"session_id","text","tokens","latency_ms"}` or `{"session_id","error"}`
- stderr: `{"status":"preparing|ready|error", ...}` — the Rust provider gates spawn on a
  stderr `ready`. **Never** print status to stdout (it corrupts the data channel).
- env: `EOCON_MLX_MODEL` (HF id), `EOCON_COREAI_MODEL` (path to .aimodel)

## 5. The #1 landmine: MLX needs xcodebuild, not `swift build`

`swift build` compiles the Swift/C++ but does **not** compile MLX's Metal shaders, so the
binary dies at runtime with `Failed to load the default metallib`. `xcodebuild` (via
`scripts/build-mlx.sh`) emits `mlx-swift_Cmlx.bundle/Contents/Resources/default.metallib`
next to the executable. **The binary and that bundle must travel together**; the orchestrator
must spawn the xcodebuild product, not the `swift build` one. Metal Toolchain is required
(already installed on the dev machine). MLX cannot run in the iOS Simulator.

## 6. 3.x migration status (branch `mlx-3x-migration`) — READ BEFORE CONTINUING

**Done & compiling** (swift build + xcodebuild, against mlx-swift-lm 3.31.3 / mlx-swift 0.31.4):
- `MLXBackend` uses one `ChatSession` per `session_id` → isolated `KVCache`, true cross-turn
  reuse (replaces 2.x per-turn re-prepare).
- `WiredMemoryAdmission` uses `WiredSumPolicy(cap: nil)` → GPU budget derived at runtime
  (scales 64 GB → 512 GB). Inference brackets with `ticket.start()/end()` (NOT
  `withWiredLimit { }` — the closure captures the actor-isolated session and Swift 6 rejects
  sending it into the nonisolated method).

**Fragile pins (the documented 3.x HF adapters break against their own latest deps):**
- `swift-tokenizers` pinned `0.5.0..<0.6.0` — `swift-tokenizers-mlx 0.3.0` calls non-throwing
  `encode/decode`; they became throwing in 0.6+.
- `swift-hf-api` pinned `0.2.2..<0.3.0` — `swift-hf-api-mlx 0.2.0` uses `HubClient`, renamed
  `HFClient` in 0.4.x.

**BLOCKER:** with the pinned-old `swift-hf-api 0.2.x`, `HubClient.default` **stalls the model
download at ~4%** (exit 124 on timeout). The 2.x `HubApi` path downloads the *same* model
fine, so it is the stale downloader adapter, not the migration.

**Two ways forward for 3.x (pick one):**
1. **Local-dir load (recommended to finish validation fast):** bypass `HubClient` with the
   local loader `loadContainer(from: directory, using: TokenizersLoader())` (in
   `swift-tokenizers-mlx`'s `Convenience.swift`). Pre-download the model with the 2.x path (or
   `huggingface-cli`) and point at the local dir. This validates ChatSession + KV + wired
   memory end-to-end without the broken downloader.
2. **Wait for / switch downloader:** track healthier `swift-hf-api-mlx` / `swift-hf-api`
   releases, or write a tiny `Downloader` conformance backed by the working swift-transformers
   `HubApi` (2.x) and pass it to `loadContainer(from:using:)`.

## 12. Core AI Gemma3 conversion validation (2026-06-23 follow-up)

The `RootLedger-Gemma3-12B-NPBP-Abliterated-v3-Fused` → Core AI conversion pipeline was
validated against the original 4-bit MLX checkpoint and HuggingFace:

- **Source weights are good.** The original 4-bit MLX checkpoint generates coherent chat
  output when prompted with the Gemma-3 chat template.
- **Dequantization is good.** The FP16/BF16 dequantized checkpoint
  (`...-Dequantized/`) produces identical generation with HuggingFace
  `Gemma3ForCausalLM`.
- **Apple's `Gemma3ForCausalLM` matches HF.** Loading the dequantized weights into
  `coreai_models.models.macos.gemma3_text.Gemma3ForCausalLM` and using the correct
  `KVCache` layout yields the same top-20 tokens and coherent chat output.
- **The "garbage" output was a prompt-formatting issue, not a conversion bug.** Both HF
  and Apple's model repeat or stall on raw text (e.g. `"hello"`) because the checkpoint is
  chat-tuned. Applying the Gemma-3 chat template fixes generation.

Key technical notes for future work:

- Apple's `KVCache.create_cache_tensors()` returns shape
  `(n_layers, batch, n_kv_heads, max_seq_len, head_dim)`. Do **not** use
  `(batch, n_layers, ...)`.
- The MLX-fused checkpoint omits `lm_head.weight` because embeddings are tied. Before
  loading into `Gemma3ForCausalLM`, add `lm_head.weight` as a reference to
  `model.embed_tokens.weight`.
- Conversion helper script: `scripts/convert_gemma3_coreai.py`. It uses the standard
  `coreai_models.export.pipeline` and is structurally sound.

Action item for the Core AI sidecar: ensure the inference path applies the model's chat
template (from the bundled `tokenizer_config.json`) before encoding the prompt, otherwise
chat-tuned models will appear to produce garbage.
